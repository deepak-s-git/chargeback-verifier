# Domain Model

**DisputeShield — the Pydantic models and enumerations that every pipeline stage reads and writes.**

*Scope: the domain layer of the rebuilt DisputeShield backend — the models in `src/domain/models.py`, the enumerations in `src/domain/enums.py`, and how they persist to SQLite. Every field, type, and enum value below is verified against the current source with `path:line` citations. Verified 2026-08-26 against the rebuilt engine. ## 1. Orientation

The domain model is the shared vocabulary of the system: the extractor proposes `ExtractedFact`s, the verification stages turn facts into `Requirement`s and `Claim`s, the analysis stages emit `Contradiction`s, a `TimelineEvent` sequence, and an `EvidenceScore`, and everything is compiled into an `EvidencePackage` hanging off a single `DisputeCase`. Every model is a `pydantic.BaseModel` (`src/domain/models.py:6`), so validation, defaults, and JSON serialization are uniform across the API, the pipeline, and the database layer.

Three conventions run through the model set:

- **Prefixed identifiers.** Cases, evidence, and claims carry type-tagged IDs generated by `generate_case_id` / `generate_evidence_id` / `generate_claim_id` (`src/domain/models.py:35-47`) and enforced by `field_validator`s: `CASE-…` (`:206-212`), `EV-…` (`:83-89`), `CLM-…` (`:119-125`).
- **Timezone-aware UTC everywhere.** All default timestamps come from `now_utc()`, which returns an aware UTC datetime rather than the deprecated naive `datetime.utcnow` (`src/domain/models.py:9-16`).
- **Grounding by hash.** `Provenance` carries a SHA-256 `content_hash` with a `compute_hash` classmethod (`src/domain/models.py:56-59`); this is what lets the verifier prove a fact traces back to unaltered source bytes.

## 4. Fields that are `str`, not `Enum` (and why)

A handful of fields describe a closed, documented domain yet are typed as plain `str`. This is deliberate: these are **closed-but-documented domains kept as strings to avoid coupling** the model layer to an enum that other layers would then have to import and stay in lockstep with. The frontend `types.ts` mirrors exactly these fields as string *unions*, so the contract is documented on both sides without a hard enum dependency crossing the boundary.

| Field | Location | Documented domain |
|---|---|---|
| `Requirement.strength` | `src/domain/models.py:134` (mirrors `RequirementDefinition.strength`, `src/domain/rules.py:15`) | `REQUIRED` / `STRONG` / `SUPPORTING` |
| `Contradiction.severity` | `src/domain/models.py:150` | `LOW` / `MEDIUM` / `HIGH` |
| `Contradiction.type` | `src/domain/models.py:151` | Mirrors `ContradictionType.value` — a `ContradictionType` enum **does** exist (`src/domain/enums.py:121-129`), but the detectors store its `.value` string rather than the enum |
| `TimelineAnomaly.severity` | `src/domain/models.py:96` | `LOW` / `MEDIUM` / `HIGH` |
| `TimelineEvent.event_type` | `src/domain/models.py:105` | `PAYMENT` / `ACCESS` / `AUTH` / `COMMUNICATION` (illustrative) |

Note the contrast within `TimelineAnomaly`: `severity` is a plain `str`, but `type` **is** the `TimelineAnomalyType` enum (`src/domain/models.py:94`). The enum is used where the value set is fixed and machine-driven; the string is used where the value is a documented label the model layer does not need to enforce.

## 5. Persistence

The domain models are stored in SQLite. The schema is defined in `src/database/migrations.py`; the database path is environment-configurable via `DISPUTESHIELD_DB`, defaulting to `disputeshield.db` (`src/database/db.py:31`). Connections are short-lived and configured with `foreign_keys=ON` and `journal_mode=WAL` (`src/database/db.py:34-38`).

Each core model maps to one table:

| Model | Table | Line |
|---|---|---|
| `DisputeCase` | `cases` | `src/database/migrations.py:75-93` |
| `EvidenceItem` | `evidence_items` | `src/database/migrations.py:96-107` |
| `ExtractedFact` (with `Provenance` flattened into `source_file` / `source_location` / `content_hash`) | `extracted_facts` | `src/database/migrations.py:110-122` |
| `Claim` | `claims` | `src/database/migrations.py:125-134` |
| `TimelineEvent` (with its `anomalies`) | `timeline_events` | `src/database/migrations.py:137-149` |
| `Contradiction` | `contradictions` | `src/database/migrations.py:152-164` |
| `AuditLogEntry` | `audit_log` | `src/database/migrations.py:167-179` |

`Requirement`, `ScoringFactor`, `EvidenceScore`, and `EvidencePackage` have no dedicated table of their own; they are computed products carried on the case and its package rather than independently persisted rows.

**Self-healing schema.** Older on-disk databases are reconciled forward by `_reconcile_columns` (`src/database/migrations.py:52`), which adds any post-v1 nullable columns an older schema is missing. It is idempotent — a no-op on a freshly created database and a one-time repair on an older one.

## 6. A note on intentionally-unused enum values

Several enum values are defined but never emitted by the current flow. They are kept for **forward-compatibility and defensive completeness** — so consumers can pattern-match exhaustively and the vocabulary can grow without a schema change — but the honest state today is that the engine does not produce them:

- **`RequirementStatus.CONTRADICTED`** and **`RequirementStatus.NOT_APPLICABLE`** — the requirement engine emits only `SATISFIED` / `PARTIALLY_SATISFIED` / `MISSING` (`src/verification/requirement_engine.py:71-76`).
- **`ClaimStatus.NEEDS_REVIEW`** — `verify_claim` emits only `VERIFIED` / `BLOCKED` (`src/verification/claim_verifier.py:69,72`).
- **`ContradictionType.TIMELINE_ORDER`** — the detectors emit `USAGE_BEFORE_PURCHASE` / `FUTURE_TIMESTAMP` instead (`src/verification/contradiction.py:160,184`).
- **`TimelineAnomalyType.IMPOSSIBLE_ORDER`**, **`TimelineAnomalyType.SUSPICIOUS_GAP`**, and **`TimelineAnomalyType.MISSING_EXPECTED_EVENT`** — `build_timeline` emits only `FUTURE_TIMESTAMP` / `DUPLICATE_EVENT` (`src/verification/timeline_builder.py:92-111`).

If you are reasoning about what the system can actually output today, treat the lists above as reserved-but-inert. They are documented here rather than quietly pruned so the gap between the defined vocabulary and the emitted vocabulary is explicit.
